# Sandbox Choice — Code Mode MCP (Exercise B)

## Decision: `isolated-vm`

We use [`isolated-vm`](https://www.npmjs.com/package/isolated-vm) (v6.x), which runs each script in a dedicated V8 isolate — a separate JavaScript engine instance with its own heap, its own microtask queue, and no shared object references to the host Node.js process.

---

## Threat Model

In Code Mode the MCP server executes JavaScript programs generated by an LLM. That code is untrusted by definition — it may be buggy, prompt-injected, or deliberately hostile. The sandbox must defend against:

1. **Filesystem access** — `require('fs')`, `import('fs')`, or equivalent built-ins reading or writing files outside the proxy.
2. **Network access** — `fetch`, `http`, `net`, or DNS exfiltrating state or pulling remote code.
3. **Process escape** — reaching `process`, `child_process`, environment variables, or the host module graph.
4. **Memory exhaustion** — unbounded allocation crashing or stalling the server.
5. **Wall-clock exhaustion** — an infinite loop blocking subsequent requests.
6. **State smuggling** — retaining a live reference to a host object across calls and observing or mutating it later.
7. **Bypassing the read/write split** — a read-context program reaching a write method via prototype walking or global inspection.

A runtime that gives the model anything resembling the standard Node.js environment fails this threat model immediately. The candidate runtime must supply *only* what is explicitly bridged, and nothing else.

---

## Why `isolated-vm` Over the Alternatives

| Sandbox | Isolation level | Threats it fails | Verdict |
|---|---|---|---|
| `isolated-vm` | Separate V8 isolate — own heap, own microtask queue, no host built-ins | None of 1–7 | **Chosen** |
| `node:vm` | Separate global object, **same V8 isolate and heap as the host** | 1, 2, 3, 6, 7 | Rejected |
| `RestrictedPython` | Python AST rewriting + limited builtins | Wrong language for the TypeScript DSL; threat model doesn't apply | Rejected |
| subprocess + timeout | OS-level process boundary | Defends 1–6 in principle; loses bridge ergonomics, adds high per-call cost | Rejected |

### Why `node:vm` fails

`node:vm` is the most tempting alternative because it ships with Node and requires no native build. It is also unsafe for this use case — Node's own documentation states "Do not use `node:vm` to run untrusted code."

`node:vm` provides **context isolation, not engine isolation**. The script runs in a fresh global object but in the *same V8 isolate* as the host. The documented escape is structural, not a CVE:

```js
this.constructor.constructor('return process')()
```

This pattern reaches the host's `process` object from inside a `node:vm` context because both share the same V8 heap. Prototype chain attacks, shared `ArrayBuffer` views, and `globalThis` leaks are all in the same family. Against the threat model: `node:vm` does not stop filesystem access (1), network access (2), process escape (3), state smuggling (6), or bypassing the read/write split (7).

### Why subprocess is not the right shape

A subprocess gives strong OS-level isolation but is rejected on engineering grounds. Every `radar` method call would have to be serialised to JSON over stdio, deserialized on the other side, and the result serialised back. Multi-step programs (`addTechnology` → `assign` → `commit`) become a second RPC protocol layered on top of MCP. Per-call subprocess startup cost is also in the tens to hundreds of milliseconds — wrong for an interactive tool. `isolated-vm` achieves comparable isolation at low single-digit milliseconds per call, with bridged proxy methods looking like ordinary synchronous calls inside the script.

---

## How the Boundary Is Enforced

`isolated-vm` is the only candidate that satisfies the full threat model at the engine level:

- **Separate heap**: the host's prototype chain, primordials, and object graph are unreachable because they live in a different V8 isolate. There is no `this.constructor` escape path.
- **Explicit data transfer**: arguments crossing the boundary are deep-copied via `{ copy: true }` through `ivm.Reference`. The program cannot retain a live handle to a host object, and the host cannot accidentally leak mutable state into the isolate.
- **Resource limits enforced by V8**: the 5,000 ms wall-clock timeout and 128 MB memory cap are enforced by the engine itself, not by cooperative checks the model-authored code could subvert.
- **Structural read/write split**: the `search()` runner binds only `READ_METHODS` into the isolate global. Write methods (`addTechnology`, `assign`, `move`, `removeAssignment`, `commit`) are simply absent — `typeof radar.commit` is `undefined` inside a read program. There is nothing for an adversarial program to find.

---

## Memory and Timeout Budget

Each isolate is created with `memoryLimit: 128 MB` and code runs under `timeout: 5,000 ms`. Both are configurable via `SandboxOptions`. The isolate is `dispose()`d in a `finally` block after every call, so memory is released even if the code throws or times out.

---

## Trade-offs Accepted

- **Native build dependency.** `isolated-vm` ships as a native module compiled against the Node V8 ABI. `npm install` takes longer on a fresh machine and must be redone when switching Node major versions.
- **Node version pin.** Node 26 changed the V8 ABI in a way that breaks `isolated-vm` 6.x. The server is pinned to **Node 22 LTS**, documented in `package.json` (`"engines": { "node": ">=22 <24" }`) and in the README.
- **No native async inside the isolate.** Bridged calls return synchronously to the model via `applySync`. Long-running async work must be orchestrated on the host side.
- **Residual V8 trust.** Like any JavaScript sandbox, this design assumes V8 itself is sound. An undisclosed V8 vulnerability could in principle bypass the isolate boundary. This is the smallest residual risk available among the candidate runtimes — V8 is the most-hardened JavaScript engine in production use.

These trade-offs are acceptable: the native build cost is a one-time setup concern, the Node pin is documented and stable, and the residual V8 risk is lower than the demonstrably broken isolation of `node:vm`.
