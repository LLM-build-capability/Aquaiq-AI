 # Sandbox Choice — Tech Radar MCP Server (Variant 2)

  **Author:** Pavitra
  **Branch:** pavitra/exercise-b
  **Variant:** V2 — Constrained domain metamodel (Stack.TechRadar)

  This document records the sandbox runtime selected for the Code-Mode MCP server, the threat model it must defend, the alternatives considered, and the trade-offs accepted in choosing it.

  ---

  ## Overview

  In Code Mode, the MCP server executes JavaScript programs generated by the LLM. Because this code is untrusted by definition, it must run in a strongly isolated environment that has no path to the host filesystem, network, or process. The
  runtime must also be efficient enough to invoke per request, and ergonomic enough to bridge a typed `radar` proxy across the isolation boundary.

  The chosen runtime is **isolated-vm**, which executes each script in a dedicated V8 isolate.

  ---

  ## Purpose

  The sandbox sits between the MCP tool entry point and the host-side `RadarProxy`. Its responsibilities are:

  - Compile and run model-authored JavaScript without granting it access to the host process.
  - Bridge a small, frozen `radar` object into the isolate so the program can call validated proxy methods.
  - Enforce wall-clock and memory limits so a misbehaving program cannot stall or exhaust the server.
  - Capture `console.log` output for debugging while keeping `stdout` clean for MCP framing.

  ---

  ## Threat Model

  The sandbox is the trust boundary between two parties with very different assumptions:

  - **The host.** Trusted. Owns `data/config.json`, the filesystem, the network, the MCP transport, and the `RadarProxy` implementation. Validation logic and governance rules live here.
  - **The model-authored program.** Untrusted. Generated by an LLM in response to a user prompt. Treated as adversarial input — it may be buggy, prompt-injected, or deliberately hostile.

  The threats the sandbox must defend against are concrete:

  1. **Filesystem access.** A program reads or writes files outside `data/config.json` by calling `require('fs')`, `import('fs')`, or any equivalent built-in.
  2. **Network access.** A program exfiltrates state or pulls in remote code via `fetch`, `http`, `net`, or DNS.
  3. **Process escape.** A program reaches `process`, `child_process`, environment variables, or the host's module graph.
  4. **Memory exhaustion.** A program allocates without bound to crash or stall the server.
  5. **Wall-clock exhaustion.** A program enters an infinite loop and blocks subsequent requests.
  6. **State smuggling between calls.** A program retains references to host objects, then mutates or observes them on a later call.
  7. **Bypassing the read/write split.** A program in a read context reaches a write method by walking prototypes or globals.

  What is **out of scope** for the sandbox: validating the *semantics* of mutations (kebab-case ids, ring transitions, referential integrity). Those are domain rules and live in `RadarProxy`. The sandbox's job is to ensure that the only way to
  affect state is by calling a proxy method — not to police what those methods do.

  A runtime that gives the model anything resembling Node.js fails this threat model on contact. The candidate runtime must give the program *only* what is explicitly bridged, and nothing more.

  ---

  ## Design Decision

  **Selected:** `isolated-vm` — a Node.js binding around V8 isolates.

  Each call to `execute` (or `search`) creates a fresh isolate, compiles the model's code inside it, injects the bound `radar` global, and runs it under a 5-second timeout and 128 MB memory cap. The isolate has no `require`, no `process`, no
  `fs`, and no network — only the explicitly bridged proxy methods cross the boundary.

  `isolated-vm` is the only candidate runtime that satisfies the full threat model. A V8 isolate is a separate instance of the JavaScript engine: its own heap, its own microtask queue, its own object graph. The host's globals are not reachable
  through any prototype walk, because they live in a different isolate entirely. Memory and wall-clock limits are enforced by V8, not by cooperative checks the program could subvert. Arguments crossing the boundary are deep-copied through
  `ivm.Reference`, which closes the state-smuggling vector — the program cannot retain a live handle to a host object, and the host cannot leak one in the other direction. The read/write split is enforced structurally: the read isolate never has
  write methods bound to its global, so there is nothing for an adversarial program to find. Together this addresses threats 1–7 directly, with the residual risk being undisclosed V8 vulnerabilities — an acceptable position given that V8 is the
  most-hardened JavaScript runtime in production use.

  ---

  ## Comparison With Alternatives

  | Runtime | Isolation level | Threats it fails | Verdict |
  |---|---|---|---|
  | **isolated-vm** | Separate V8 isolate per call: own heap, own microtask queue, no host built-ins | None of 1–7 in the threat model | **Selected** |
  | `node:vm` | Separate global object, **same V8 isolate and heap as the host** | 1, 2, 3, 6, 7 | Rejected |
  | RestrictedPython | Python AST rewriting | Wrong language for the DSL; threat model doesn't apply | Rejected |
  | Subprocess + timeout | OS-level process boundary | Defends 1–6 in principle, but loses bridge ergonomics and adds high per-call cost | Rejected |

  ### Why `node:vm` Fails the Threat Model

  `node:vm` is the most tempting alternative because it ships with Node and needs no native build. It is also unsafe for this use case, and the spec calls this out directly.

  `node:vm` provides **context isolation, not engine isolation**. The script runs in a fresh global object, but in the *same* V8 isolate as the host. That means the host's prototype chain, the host's primordials, and the host's object graph are
  reachable from inside the script — and the documented escape pattern (`this.constructor.constructor('return process')()`) has been rediscovered repeatedly because it is structural, not a bug. Node's own documentation warns against using
  `node:vm` as a security boundary.
  
  Concretely, against the threat model: `node:vm` does not stop filesystem access (1), does not stop network access (2), does not stop process escape (3), does not prevent state smuggling because objects can leak across the context boundary by
  reference (6), and does not enforce the read/write split because a sufficiently determined program can walk back to the host realm and find whatever it wants (7). Memory and timeout (4, 5) are partially addressable but cooperative.

  The threat model is *not* OK with `node:vm`. Any runtime where the adversarial program shares an engine with trusted host code is a runtime that depends on the program's good behaviour, which is exactly the assumption Code Mode cannot make.

  ### Why a Subprocess Is Not the Right Shape

  A subprocess gives strong OS-level isolation and would defend most of the threat model. It is rejected on engineering grounds, not security grounds: every `radar` method call would have to be marshalled across stdio, serialized to JSON, and
  re-deserialized on the other side. Multi-step programs (`addTechnology` → `assign` → `commit`) become a second RPC protocol layered on top of MCP, and the per-call subprocess startup cost is in the tens to hundreds of milliseconds — wrong for
  an interactive tool. `isolated-vm` achieves comparable isolation at low single-digit milliseconds per call, with the proxy bridge looking like ordinary method calls inside the script.

  ## Implementation Approach

  The sandbox module exposes two entry points: a read-only runner and a read-write runner. Both compile the supplied code in a fresh isolate and inject a `radar` global; the difference is which proxy surface is bound.

  ```ts
  import ivm from "isolated-vm";

  export async function runReadOnly(code: string, proxy: RadarReadProxy): Promise<unknown> {
    const isolate = new ivm.Isolate({ memoryLimit: 128 });
    const context = await isolate.createContext();
    const jail = context.global;

    // Bridge only the read surface — write methods are absent from the isolate global.
    await bindRadar(jail, {
      listTechnologies: proxy.listTechnologies.bind(proxy),
      listTeams:        proxy.listTeams.bind(proxy),
      listAssignments:  proxy.listAssignments.bind(proxy),
      getAssignment:    proxy.getAssignment.bind(proxy),
      validate:         proxy.validate.bind(proxy),
    });

    const script = await isolate.compileScript(code);
    return script.run(context, { timeout: 5_000 });
  }
  ```

  The read-write runner binds the full `RadarProxy` surface, including `addTechnology`, `assign`, `move`, `removeAssignment`, and `commit`. Because the read isolate never receives those bindings, `typeof radar.commit` is `undefined` inside a
  read program — the read/write split is structural, not advisory.

  Each bridged method uses `ivm.Reference` to call back into the host. Arguments are deep-copied across the boundary, so the isolate cannot retain references to host objects, and the host cannot accidentally expose mutable state to the isolate.

  ---

  ## Benefits
  
  - **True isolation.** The isolate has its own V8 heap, its own microtask queue, and no access to Node built-ins. The only host capability available is whatever is explicitly bridged.
  - **Resource limits.** Wall-clock timeout (5 seconds) and memory cap (128 MB) are enforced by V8 itself, not by cooperative checks.
  - **Structural read/write split.** The read runner literally does not bind write methods, so read-only programs cannot mutate state regardless of what the model attempts.
  - **Low per-call overhead.** Isolate creation is in the low single-digit milliseconds — fast enough to use per request without pooling.
  - **Clean integration.** Bridged proxy methods look like ordinary method calls inside the isolate, so the model can write idiomatic JavaScript without learning a new RPC convention.

  ---

  ## Trade-offs

  - **Native build dependency.** `isolated-vm` ships as a native module and must be compiled against the host's Node ABI. This adds an `npm install` cost and ties the project to a specific Node major version.
  - **Node version pinning.** The current release builds cleanly on Node 22 but fails on Node 26. The project documents this constraint and expects developers to use Node 22 in `exercise-b/`.
  - **No native async inside the isolate.** Bridged calls return synchronously to the model; long-running async work must be orchestrated on the host side rather than awaited inside the script.
  - **Memory cap is per-isolate, not per-server.** Concurrent calls each get their own 128 MB ceiling, so the server's worst-case footprint scales with concurrency.
  - **Residual trust in V8.** Like any JavaScript sandbox, this design assumes V8 itself is sound. An undisclosed V8 vulnerability could in principle bypass the isolate boundary; this is the smallest residual risk available among the candidate
  runtimes.

  ---
  
  ## Conclusion

  `isolated-vm` is the only option in the candidate set that satisfies the threat model: it isolates at the engine level rather than the context level, enforces resource limits in V8, prevents state smuggling through deep-copied arguments, and
  makes the read/write split a structural property of the binding rather than a policy. `node:vm` is rejected because it shares an engine with the host and therefore cannot defend against an adversarial program; a subprocess is rejected because
  it would defend the threat model but at an engineering cost that breaks the proxy bridge. The native-build dependency and Node-version pin are acceptable prices for a runtime whose entire purpose is to execute model-authored code safely.
